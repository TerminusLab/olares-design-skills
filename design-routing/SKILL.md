# design-routing

**分发器。** 用户不该需要记得有哪些 skill，也不该需要说对触发词。

看到任何会改变视觉的请求，先落到这里，判档位、选路径、挂底线，然后直接执行——**不要反问"你想用哪个 skill"**。

---

## 三条底线：无论走哪条路径都要挂上

1. **读 [references/constraints.md](references/constraints.md)**——三个卡点、复用优先级、工具类优先、不许丢的东西。
2. **所有视觉值必须落在词汇表内**。目标仓库的 `docs/design-system-inventory.md` 就是值集合；没有或已过期先跑 `design-probe`。找不到对应值走卡点 2，**不要静默硬编码**。
3. **收尾跑一次静态校验**（`design-verify` 第一层），扫本次改动文件有没有词汇表之外的 hex / px。改一行也要扫，很快。

这三条对**所有**路径生效，包括下面那些通用设计 skill。

## 路由表

| 用户大概会这么说 | 路由到 | 档位 |
|---|---|---|
| "做一个 XX 页面 / 功能"（还没有设计稿） | `design-pipeline` | 新建，全链路 |
| 给了 figma 链接 + "实现 / 还原 / 按这个改" | `design-implement`（Olares/Quasar 项目叠加 `design-implement-olares`） | — |
| "这个页面重做一版视觉 / 按新设计改版" | `design-pipeline`，从阶段 2 进 | 改造 |
| "改一下间距 / 换个颜色 / 调字号 / 换个图标 / 这个组件样式改改" | `design-implement` 第 1 步 + 第 3 步，再跑 `design-verify` 静态层 | **小修** |
| "摸清这个项目有哪些 token / 组件能用" | `design-probe` | — |
| "检查一下和设计对不对 / 有没有硬编码颜色 / 差在哪" | `design-verify` | — |
| "这个页面在手机上不行 / 适配一下移动端" | `adapt` + 共享约束第七节（多视口） | 视改动量定 |
| "太单调 / 加点颜色 / 排版难看 / 加点动效 / 太吵太花 / 太平淡" | 对应的通用设计 skill，**但按下一节加护栏** | 小修 |

**判不准档位就问一句**"这次是新建、改造，还是小修？"——比走错档位浪费半小时便宜。

## 通用设计 skill 要加护栏

`polish` / `layout` / `colorize` / `animate` / `critique` / `typeset` / `impeccable` / `bolder` / `quieter` / `distill` / `delight` / `optimize` / `overdrive` / `adapt` 这些 skill 很好用，但它们**不知道这个项目有 token 体系**——`colorize` 的职责就是加策略性的颜色，它会直接写 hex；`typeset` 会直接写 `font-size`。

不加护栏就等于开了一条绕过全部约束的后门，而且是**最容易被走的那条**（"这个页面太单调了"比"按 figma 改 UI"顺口得多）。

所以用它们之前、之后各加一步：

- **之前**：先读 `docs/design-system-inventory.md`，把词汇表交给它——「你可以用的颜色只有这些，间距只有这些档位」。
- **之后**：跑 `design-verify` 静态层。它们产出的值只要不在词汇表内，一律按卡点 2 处理。

**不要因为有护栏就放弃这些 skill**。视觉判断力是它们的长处，词汇表约束是我们的要求，两件事不冲突。

## 小修最短路径（直接在这里就能开工）

判定为小修（改间距 / 换颜色 / 调字号 / 换图标 / 微调某个组件样式）且**没有设计稿**时，不必先把 `design-implement` 和共享约束通读一遍。四步就够：

1. **拿词汇表** —— 读目标仓库 `docs/design-system-inventory.md` 里本次要用的那一类（改间距就只看间距表）。没有盘点 → 跑 `design-probe` 的**最小可用盘点**，只扫这一类，不需要 Figma `fileKey`。
2. **先找工具类，再写 CSS** —— 类名 = 前缀 + token 名原样，不自己加减连字符（`body1` → `text-body1`，不是 `text-body-1`，后者是不生效的死类）。颜色用语义层变量，不硬编码亮色值。
3. **找不到对应值就停下来问**（卡点 2）—— 不要静默硬编码。确实必须保留自定义值时，紧邻上一行写 `/* design-exempt: <原因> */`。
4. **改完扫一遍** —— `design-verify` 静态层，只扫本次改动的行。改一行也要扫，很快。

超出下面任一条时，**回到完整路径**读 `design-implement`（Olares / Quasar 项目再叠 `design-implement-olares`）：

- 有 Figma 设计稿要对；
- 要新增或改动组件结构，不只是换值；
- 要导出 SVG / 做暗色变体；
- 改到了被多处复用的组件（要做旧消费者回归）；
- 跨了三类以上视觉值。

这一节存在的理由：改一个间距要先读上千行文档的话，实际结果是绕过整套体系直接改。**能拿到 80% 约束的短路径，比没人走的完整路径有用。**

## 什么时候不该路由到这里

这些词很容易误伤——"太丑""对不齐"在非 UI 语境里同样常用。命中关键词不等于这是一份视觉工作：

- **纯逻辑改动**（数据获取、状态管理、路由、接口、算法）——那不是视觉工作，别硬套。
- **评价代码而非界面**（"这段代码写得太丑""结构乱"）——交给 `code-review` 那一条线。
- **非前端文件的对齐 / 排版**（JSON、日志、CSV、Markdown 表格对不齐）——跟设计体系无关。
- **设计工具本身的使用问题**（"Figma 怎么建变量""插件装不上"）——那是工具支持，不是落地。
- **用户明确点名了某个 skill**——照他说的做。

改动**同时**涉及视觉和业务逻辑时：视觉部分走这里，逻辑部分走共享约束的**卡点 3**（停下来问）。

拿不准时问自己一句：**这次会不会改到 `.vue` / `.tsx` / `.scss` 里的视觉值？** 不会就不是本 skill 的活。
