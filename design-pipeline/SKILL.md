# design-pipeline

链路的**编排层**：定阶段、定交接产物、守卡点。

**不重写** Figma API 细节——那些在官方 skill 里（`figma-generate-design` 478 行、`figma-use` 435 行），本 skill 只负责在正确的时机委派过去。

**先读 [references/constraints.md](references/constraints.md)**（四个卡点、记账规则、不许丢的东西、复用优先级、失控预算、收尾报告格式）。术语见 [references/glossary.md](references/glossary.md)。

---

## 0. 先定档位

按改动性质先分三档，再看要不要叠长页面，**别一刀切**：

| 档位 | 什么情况 | 怎么走 |
|---|---|---|
| **新建** | 做一个不存在的页面 / 功能 | 全链路，阶段 1→7 |
| **改造** | 既有页面重做视觉 | 跳过阶段 1（需求澄清），从阶段 2 开始 |
| **小修** | 改间距、换图标、调个颜色 | **不进本 skill**：`design-implement` 第 1 步（拿词汇表）+ 第 3 步（落地），再跑 `design-verify` 静态层 |
| **长页面** | 单页并列 section **≥ 4**，或存在结构重复的模块，或估算一次写完接近输出上限 | 全链路，但阶段 5 拆为 3.5 → 5a → 5b，且多一个卡点 4 |

长页面档是**新建 / 改造的叠加项，不是第四种并列情况**——同一个多模块页面既可能是新建也可能是改造，两者都要叠上本档的拆分。先定新建还是改造（决定要不要走阶段 1），再看是否命中长页面判据（决定阶段 5 怎么走）。

**「长页面」指的是结构，不是页面类型。** 控制台仪表盘、设置页、详情页、长表单、文档页，只要单页内并列多个模块就都算；反过来，一个只有两屏但两屏结构相同的页面也命中（第 2 条判据）。别按页面名字对号入座。

拿不准就问一句"这次是新建、改造，还是小修？"——比走错档位浪费半小时便宜。

**拿不准就当长页面处理。** 误判为长页面的代价是多一次确认，而且清盘清单本身不浪费（它顺带查出缺件）；误判为普通页面的代价是后半页重写。

## 委派怎么写（重要）

需要用到别的 skill 时，**按名字引用**："使用 `figma-generate-design` skill"，让 agent 从自己的可用 skill 列表里找。

找不到时才用 glob 兜底搜文件：`~/.cursor/plugins/cache/cursor-public/figma/*/skills/<name>/SKILL.md`。

**绝不写死带 hash 的路径**（`.../figma/07316dd.../`）——那是插件的 commit SHA，一升级就全断，而且断了不报错。

glob 也搜不到时，按 `references/constraints.md` **第十一节**处理：必需依赖（Figma 那三个）停下来说，可选依赖降级并记账。**不要自己临时实现 Figma API 调用。**

## 阶段 1 · 需求澄清

只问三件事，问完就走，别开需求评审会：

1. **谁在用**——用户角色。
2. **什么场景**——从哪来、要完成什么。
3. **怎么算成功**——做完之后什么变了。

产出两份清单，写进运行记录：

- **页面清单**：要做哪几个页面 / 视图 / 弹层。
- **状态清单**：每个页面除理想态之外的形态——loading、empty、error、无权限、超长文本。

状态清单必须在这一步列出来。Figma 稿几乎从不画非理想态，等落地时才发现"空态没设计"就晚了。

> 改造档跳过本阶段，但**仍要补状态清单**——既有页面已有的非理想态不能在重做中丢掉。

## 阶段 2 · 探测设计体系

委派 `design-probe`。

产出目标仓库的 `docs/design-system-inventory.md`（盘点快照）。已有且未过期就直接用，不重扫。

**这一步可能直接触发卡点 2**：代码侧没有 token 体系、或 Figma 侧没有设计系统库。停下来给方案，别硬着头皮往下走——后面所有"映射到词汇表"的动作都会落空。

## 阶段 3 · 在 Figma 生成真图层

委派 `figma-generate-design`（它会要求同时加载 `figma-use`）。

本 skill 只管三件它不管的事：

**文件与图层组织**——每个项目固定一个 Figma 文件，`fileKey` 记在盘点文档里；链路产物放专用 page；frame 命名 `<feature>/<viewport>`（如 `账单详情/pc`、`账单详情/mobile`）。散落成多个文件的话，续跑时找不回上次的节点。

**两个视口都要**——PC 与移动各生成一套。只做一套等于把移动端留给"落地时随便适配一下"。生成移动稿前先看 `references/constraints.md` **第七节**的必查项（热区 ≥ 44px、不依赖 hover、导航抽屉改 overlay、安全区……）——这些得在**画的时候**就算进去，等落地才发现热区不够就要重画。

**状态也要画**——阶段 1 的状态清单里每一项都要有对应图层，至少 empty 和 error。

生成完把每个 frame 的节点 URL 写进运行记录。

> 已经有设计师画好的稿：跳过本阶段，直接把节点 URL 记进运行记录，进阶段 4（长页面档先进阶段 3.5）。

> **长页面档额外一条**：每个模块要有自己的顶层 frame（命名 `<feature>/<viewport>/<模块>`）。整页共用一个大 frame 时，阶段 5b 拿不到单模块链接，只能退回整页一次做完——拆分流程就此失效。拿到的是现成稿且不具备这个结构时，在阶段 3.5 把「需要拆 frame」作为清盘结论的一部分提出来。

## 阶段 4 · 卡点：设计定稿确认

**停下来。** 把每个 frame 的截图和链接给人看，等一句明确的"可以"。

拿到确认之后，**必须重新 `get_design_context` 拉一次当前状态**再落地。人很可能已经直接在图层上改过——复用阶段 3 生成时的产物等于静默丢掉这些修改，而且表面上看不出任何异常。

（细节见 `references/constraints.md` 卡点 1。）

## 阶段 3.5 · 卡点：模块清盘（仅长页面档）

非长页面档跳过本阶段，直接进阶段 4。

位置在阶段 4（设计定稿）**之前**：清盘会暴露「这两个模块其实该长得一样」这类问题，还没定稿时改图层比定稿后改便宜得多。

**不写任何代码。** 只输出一张模块清单：

| # | 模块名 | 结构类型 | 复用判断 | 需要的数据 | 非理想态 |
|---|---|---|---|---|---|
| 1 | Hero | 独有 | — | 主标题 / 副标题 / CTA | 背景视频加载失败 |
| 2 | 核心能力 | `FeatureGrid` 三列卡片 | 首次定义 | 3 条 title+desc+icon | — |
| 3 | 产品截图 | `ImageTextSplit` 左图右文 | 首次定义 | 图 + 文案 | 图片未加载 |
| 4 | 使用场景 | `FeatureGrid` 三列卡片 | **复用 #2** | 3 条 | — |
| 5 | 技术架构 | `ImageTextSplit` 右图左文 | **复用 #3**（镜像） | 图 + 文案 | — |

### 物料就绪度自检（agent 自己查，并且**先自己动手解决能解决的**）

清盘不只是拆模块，还要查一遍**物料够不够**。这是长页面档质量的地基：物料齐备 → 5a 的 props 接口定得准 → 5b 每个模块只做填充 → 逐模块验收能过 → 整页质量稳定。物料不齐时这条链在第一环就断，后面全是补救。

自检的输出**不是一张「还缺这些，你去补」的清单**，而是三路分流。这一节的全部价值在于分流本身：

| 分流 | 判据 | agent 怎么做 |
|---|---|---|
| **A 自己解决** | 有源可取、且不涉及主观判断 | **直接做完**，只在清单里写一句「已自行处理 + 怎么处理的」，不要拿来问人 |
| **B 需要物料** | 凭空造出来就是错的 | 输出**物料清单**：要什么、什么格式、给到哪、不给的后果 |
| **C 需要决策** | 不缺东西，缺的是判断 | **带上自己的建议和默认方案**再问，不要开放式提问 |

**A 类——自己做完，不要问：**

| 事项 | 怎么自解 |
|---|---|
| 图片 / 插画 / SVG 导出 | 稿里有源就直接导，按项目既有资源目录与命名放好 |
| 多倍图、暗色变体 | 稿里存在对应图层就一并导出 |
| 图标映射 | 逐个对到项目图标集；对得上就用，对不上的才进 B 类 |
| 非理想态的**结构** | loading / empty / error 的骨架按项目既有同类写法补，不必等设计稿 |
| 重复模块的差异点 | 列数、图文方向、有无角标这类能从稿里读出来的，自己读，不要问 |
| 词汇表映射 | 颜色、间距、字号照盘点结果映射 |

**B 类——列物料清单，说清要什么：**

| 缺什么 | 为什么不能自解 | 清单里要写明 |
|---|---|---|
| 终稿文案 | 文案长度决定卡片高度与换行，猜错要重排布局而非替换文字 | 哪几个模块、大致字数范围、有无字符上限 |
| 真实图片素材 | 稿里只有低清占位、无源文件；裁切比例依赖真图 | 张数、尺寸、比例、是否需要暗色版 |
| 接口字段 / 数据结构 | 字段决定 props 形状，接口改了组件跟着改 | 哪个模块、期望字段名与类型、分页与空值约定 |
| 移动端设计稿 | **绝不凭空臆造移动端设计**（见约束第七节） | 缺哪些模块的移动稿；或明确改为按断点降级 |
| 品牌资产 | logo 多版本、特定字体文件无法生成 | 具体要哪个版本、什么格式、授权是否到位 |

每项标**必须补**还是**可降级**。判断标准是：不补会导致**已写代码返工**的算必须补（文案长度、移动稿、接口字段）；只影响成品精度、能事后替换的算可降级（多倍图、暗色变体、个别图标）。全标必须补等于卡死流程，全标可降级等于这张表没用。可降级项照 `references/constraints.md` 第十节记进收尾报告。

**C 类——带建议再问：**

三个决定见下一段。要点是每一条都**先给出自己的判断和默认方案**，人只需说「按你说的」或改动其中一处。

**为什么必须分流，而不是列一张大清单。** A 类混进清单里的后果不是多几行字，而是**用一堆本可自动处理的琐事淹没真正需要人判断的那两三条**。人看到十几项时的典型反应是回一句「都可以，你继续」——于是 B 类的缺文案和 C 类的复用判断一起被放过，等于这个卡点白设了。分流之后人只面对 B 和 C，通常各只有两三条。

**为什么 C 类必须带默认方案。** 开放式提问（「你觉得这几个模块怎么处理」）的有效回复率远低于确认式提问（「我建议 #4 复用 #2，只是列数不同，可以吗」）。带了默认方案，人即使不细看也能得到一个合理结果；不带，流程就停在等回复上。

### 三个必须由人拍板的决定

清单交人后，**等三个决定**。这三个必须由人拍板，但**每条都要先给出自己的建议**——不要把空白问题丢回去：

1. **复用判断对不对**——先给出自己的判断（哪几个复用哪个、差异在哪），请人确认或纠正。可能把两个只是「看起来像」的模块归成同一类型，也可能漏掉真正的复用。这一条错了后面全歪，而且是结构性错误。
2. **哪些模块可以先不做**——先按「有更好、没也能上线」标出候选，请人拍板。明确砍掉或延后，比把注意力平均洒在十几个模块上好。
3. **哪些已有现成实现**——先照复用优先级第 1–5 档搜一遍项目，把搜到的候选连路径一起列出来请人确认，别把搜索工作推给人。导航、Footer、CTA 按钮项目里大概率已经有了，这一步不指出来就会重写一遍。

### 物料就绪门槛（进 5a 之前）

B 类里标了**必须补**的项没有解决之前，**不要进阶段 5a**。

理由是 5a 要定 props 接口，而接口形状依赖真实数据：拿 Lorem 文案和占位图定下的接口，等真文案与真字段到了就得改，而那时 5b 已经按旧接口写了好几个模块。这是长页面档里返工面积第二大的情况，仅次于漏掉结构复用。

允许**明确降级**后放行——例如移动稿确实没有，改为按断点优雅降级。但降级必须是一个被记录的决定，写进收尾报告第 5 条，不能是默认发生的事实。

清单写进运行记录。它是后面 5a / 5b 两个阶段的唯一依据，也是跳会话续跑时的交接产物。

（卡点定义与为什么需要它见 `references/constraints.md` 卡点 4。）

## 阶段 5 · 落地

委派 `design-implement`。要不要**叠加** `design-implement-olares`，按它开头的两条判据实地确认（看 `package.json` 有无 `quasar`、看有无 `--q-ink-*` 语义色与 `Bt*` 组件），不靠仓库名猜。

每落地一个页面就更新一次运行记录，别攒到最后——卡点可能隔几天才通过，中途丢了上下文就要重来。

> **长页面档不走上面这一步，改走 5a → 5b。**

### 阶段 5a · 骨架 + 公共组件（仅长页面档）

**前置条件**：阶段 3.5 物料清单里标「必须补」的项已解决或已明确降级。没满足就回 3.5，不要先搭骨架——接口形状依赖真实数据。

只做两件事，**不填任何模块内部内容**：

1. **页面骨架**——按清单顺序排好所有 section，每个只放组件调用与占位注释。
2. **公共组件的壳**——清单里标了「首次定义」的那几个结构类型，写出组件 + props 定义 + 基础布局，内容由 props 传入。

**为什么要单独拉出一个阶段：**骨架与公共组件是**全局决策**，必须在还有全页视野时一次定好；而每个模块的内容填充是**局部工作**，可以分开做。混在一起就会出现「写到第 9 个模块才发现应该抽个组件」。

本阶段定下的 props 接口同时**给 5b 划了边界**：填充时不得随意改布局，只能按接口传数据。这是控制风格漂移的关键。

骨架与组件壳完成后**先给人看一眼**再进 5b。这不是硬卡点，但接口定错了会让后面每个模块都跑偏。

### 阶段 5b · 逐模块填充（仅长页面档）

**一个模块一次，每次尽量开新会话。**

每次的输入只需四项：这一个模块的 Figma 节点链接（**不是整页链接**）、已定好的组件文件路径、词汇表、以及**已完成的上一个模块作为样板**。

样板这一项比任何描述都有效——一份已审过的模块文件包含一整套没写出来、甚至没意识到的约定：注释风格、props 命名习惯、响应式写法、图片引入方式。第一个模块没有样板可用，所以它值得多花时间审，**它就是后面所有模块的模板**。

开新会话不是麻烦，而是让每个模块拿到的注意力与单独做一个页面时相当——而单页面的完成度本来就是可接受的。

填完一个就在运行记录里勾掉一个，**粒度是模块不是页面**。页面粒度对长页面没意义：页面就是全部，勾掉它时已经没有可续跑的余地。

## 阶段 6 · 验收

委派 `design-verify`。

静态层默认跑；运行时层在能跑起来页面时跑；埋点模式默认关闭。

超 3 轮修不好就停下汇报，不要无限磨。

> **长页面档**：每填完一个模块就对它跑一次静态层，不要等十几个模块全部做完再验。放到最后会一次冒出几十条偏差，还分不清哪条来自哪个模块；而同一类错误在第二个模块就拦住，后面十个就不会重复。全页完成后再跑一次完整验收（含运行时层）。

## 阶段 7 · 收尾

按 `references/constraints.md` 第十节输出结构化报告。

链路到此为止——**不 commit、不开 PR、不部署**。那些交给 `code-review`、`split-to-prs` 等其他 skill。

## 运行记录：让链路能续跑

链路会跨会话。阶段 4 是人工卡点，可能隔几天才通过；那时新会话对之前发生过什么一无所知。

所以每条链路在**目标仓库** `docs/` 下留一份运行记录（如 `docs/design-runs/<feature>.md`），至少包含：

- 当前档位与所处阶段
- 页面清单、状态清单
- Figma `fileKey` 与每个 frame 的节点 URL
- 卡点上的决定（谁、什么时候、决定了什么）
- **长页面档还要记**：阶段 3.5 确认后的模块清单（含复用关系与被砍掉 / 延后的模块）、阶段 5a 定下的公共组件与 props 接口、以及**每个模块的完成状态与样板文件路径**
- 缺 Code Connect 映射的组件
- 降级项

**开工前先找有没有现成的运行记录**：有就从记录里的阶段接上，不要从头再问一遍需求、再扫一遍词汇表。
