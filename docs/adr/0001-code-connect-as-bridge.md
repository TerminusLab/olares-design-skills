# 0001. 用 Code Connect 做桥，不设单一真相源

日期：2026-07-30
状态：已接受

## 背景

设计到开发的链路里，同一个设计系统在两个系统里各存一份：Figma 侧的组件、变量、样式；代码侧的 design token、组件库。

两侧的命名几乎必然不一致（Figma 叫 `Gray/gray-9`，代码叫 `--q-ink-1`）。链路在中间要做两件相反的事：生成设计时用 **Figma 侧**的词汇搭图层，落地成代码时又要求映射到**代码侧**的词汇。两侧对不上，agent 只能靠名字相似度猜，猜错了不报错、只是颜色不对——这类错误最难发现，也正是过往返工的主要来源。

## 决策

**不指定单一真相源。** Figma 侧与代码侧各自演进，用 Code Connect 映射文件把两侧的组件钉死对应。

`get_design_context` 命中 Code Connect 时会直接返回映射好的代码组件，组件选择从「猜」变成「查」。

映射缺失时**不阻断**：降级为「搜项目组件库/姊妹仓库 → 停下问」，并在收尾报告记账，由人决定是否补映射。覆盖率随使用逐步上升。

## 考虑过的其他方案

**代码是真相源，Figma 设计系统由代码库反向生成。** 一致性最强，但要求 Figma 侧完全跟随代码，设计师无法在 Figma 里先行探索——而实际协作中设计师会直接改 AI 生成的图层。这条路等于否定设计师的工作方式。

**Figma 是真相源，代码 token 从 Figma 变量导出生成。** 同样一致，但代码侧的 token 往往承载 Figma 没有的东西（主题切换、构建期覆盖、平台差异）。导出生成会把这些抹平，且历史项目无法回头适配。

**不解决，运行时遇到不一致就停下问人。** 最省事，但每个组件都要问一次，链路退化成问答，与自动化目标背道而驰。

## 后果

**好的**：两侧保持各自的演进自由；设计师可以直接改图层而不破坏链路；映射一次写好长期复用；缺映射不阻断，链路第一次就能跑起来。

**坏的**：Code Connect 覆盖率低时，链路质量退回到「搜组件库 + 猜」的水平，且这个退化是渐进的、不显眼的——所以收尾报告必须显式列出缺映射的组件，否则覆盖率永远不会涨。

映射文件本身需要维护：组件重构后映射会失效，而失效不会报错。
