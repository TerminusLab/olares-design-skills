# 共享硬约束

本文件是**唯一定义源**。`design-routing` / `design-pipeline` / `design-probe` / `design-implement` / `design-implement-olares` / `design-verify` 都引用它（各自的 `references/constraints.md` 是指向本文件的软链）。

要改约束，改这里，所有引用它的 skill 同时生效。**不要**在某个 skill 里另写一份。

术语（链路 / 词汇表 / 盘点 / 桥 / 卡点 / 记账 / 降级 / 档位…）见同目录的 `glossary.md`。

---

## 一、四个卡点：停下来，等人回答

除以下四处，一律自主推进，不要为了"确认一下"打断人。

卡点 1–3 在任何档位都可能触发；**卡点 4 只在长页面档触发**（判据见下）。

### 卡点 1 · 设计定稿确认

Figma 图层生成完毕后、写任何代码之前，停下来让人确认。

不确认就写代码，等于把一个错的设计完美地实现一遍。

**卡点通过后必须重新 `get_design_context` 拉取节点当前状态**，绝不复用生成阶段的产物——人可能已经直接在图层上改过，复用等于静默丢弃这些修改，而且看起来一切正常。续跑时同理。

### 卡点 2 · 词汇表匹配不到

某个视觉值找不到足够接近的 token / 组件时，停下来问，**不要静默硬编码 hex / px**。

两种极端情况同样走本卡点，而且要在**探测阶段**就报出来，不要跑到落地时才发现。**停下来时必须带菜单**（可改，不可只说「供选」）：

**代码侧没有 token 体系**（扫不到任何设计变量，含空仓库）：

| 方案 | 含义 |
|---|---|
| **A（有 Figma 库时优先）** | 从已挂库镜像语义色 / 间距为代码 CSS 变量（或项目既有 token 格式），写入盘点；再脚手架落地 |
| **B** | 在本 Figma 文件建 local variables，开发时一对一落地 |
| **C** | 用户指定已有代码仓 / 设计系统，改去对齐那边 |

不擅自往项目里塞一套新体系。选 A 时盘点源文件必须点到镜像后的 token 文件；空仓脚手架时机见 `design-pipeline` greenfield 分支。

**Figma 侧没有设计系统库**（`get_libraries` 无可用库）：

| 方案 | 含义 |
|---|---|
| **A** | 从代码反向建库（`figma-generate-library`） |
| **B** | 引入社区 / 组织 UI kit |
| **C** | 先手工建本文件变量与组件 |

不在无库状态下硬画原始图形。

链路不假装自己完整。

### 卡点 3 · 需要改动业务逻辑

默认只改：模板结构、样式 / token、图标与资源、响应式。

**不碰**：API 调用、store、路由、数据流、事件处理的语义、既有工程约定。

确有必要改时，停下来说明改哪、为什么、影响面，等确认。

阶段 1 若勾选**演示 mock**（非接真接口）：落地只允许本地状态机 / 假数据；一旦要接真 API、改 store 或鉴权语义，仍走本卡点。

### 卡点 4 · 模块清盘确认（长页面档专属）

**触发判据（三条任一命中即算）**：

1. 单个页面里并列的 section / 模块 **≥ 4** 个；
2. 存在**结构看上去相同的模块，哪怕只有两个**——这意味着有组件可抽，而抽不抽得在写代码前定；
3. 估算一次写完会接近**单次输出上限**（模块不少，且每个都要带响应式与非理想态）。

**适用范围远不止官网首页。** 任何单页内并列多模块的结构都算：产品落地页、控制台仪表盘（多卡片加多图表）、设置页（多个并列设置组）、详情页（多个信息区）、长表单（多个字段组）、文档与帮助页。**判据看结构，不看页面叫什么名字。** 这里列的是例子，不是白名单。

**为什么阈值是 4 而不是 5。** 阈值回答的不是「多少个开始写不好」，而是「多少个开始值得先抽组件」。四个模块里出现一对重复结构已经很常见，而那一刻抽组件的成本最低。两边代价也不对称：多走一次清盘只多花几分钟，且清单本身仍然有用（它同时是缺件清单和续跑交接产物）；少走一次的代价是后半页重写。所以**拿不准就走清盘**，不要在 3 个还是 4 个上纠结——第 2 条判据存在的意义就是让模块数不够时也能命中。

命中时，**读完设计稿后先不要写任何代码**，先产出一份模块清单交人确认。清单格式、物料就绪度自检（三路分流）、以及三个必须由人拍板的决定见 `design-pipeline` 阶段 3.5。

**为什么长页面必须多一个卡点。** 短页面一次做完是可行的；长页面一次做完会同时踩上三件事，而且都不会报错：

1. **后半段静默降质**——整页节点树动辄几万 token，靠后的模块拿到的注意力显著更少，产出是「看起来像那么回事」的占位实现。输出仍是完整一页，不滚到底逐个看发现不了。
2. **撞单次输出上限**——要么自我压缩（省掉响应式、非理想态，用 `<!-- 其余同理 -->` 代替重复结构），要么中途截断。让它「继续」时前半段代码已不在上下文里，于是重新发明一套命名与间距，前后风格分叉。
3. **无法回头识别复用**——顺序往下写时，「第 9 个模块和第 3 个结构相同」这件事没有机会被发现。结果是十几个模块各写一遍，间距字号各不相同。这是架构缺失，改起来等于重写，是长页面返工成本最高的一类问题。

三件事的共同点是**先写代码就已经晚了**。清盘卡点的作用不是「确认一下」，而是把架构决定提到写代码之前。

**清盘由 agent 主动完成，而且要分流处理，不是罗列一堆问题等人回答。** 三路分流：能自己解决的（导图、映射图标、补非理想态结构、读出重复模块差异）**直接做完**，只报一句已处理；只能由人提供的（终稿文案、真实图片、接口字段、移动稿、品牌资产）输出**物料清单**，写明要什么格式、不给的后果；需要人判断的（复用对不对、哪些先不做、哪些已有实现）**带着自己的建议和默认方案**去问。

分流的意义在于**保护人的注意力**：把能自动处理的琐事一起列出来，结果是人回一句「都可以」，真正要紧的两三条被一起放过，卡点等于白设。

## 二、记账：发现了，但不停

以下情况**不**打断，记进收尾报告由人事后定夺：

- **缺 Code Connect 映射**：降级为「搜项目组件库 / 姊妹仓库既有实现 → 实在找不到才走卡点 2」，并列出本次缺映射的组件。
- **降级项**：因输入缺失只做了一部分的地方（如只有桌面稿）。
- **新写（而非复用）的组件**及原因。
- **新导出的资源**（路径、是否含暗色变体）。

## 三、落地时不许丢的东西

Figma 稿只画理想态、只画一种语言、不画交互，重写时最容易把这些丢掉：

- **i18n**：文案抽 key，Figma 里的文字**只当参考**，不硬编码。**只改增量，不改存量。**
  - **所有路径**：能复用项目已有 key 就复用；存量 key 的任一 locale **原样不动**——禁止改写、润色、「对齐 Figma」、统一语气。
  - **Olares / Quasar**（完整落地 **或** 小修）且本次有**增量**用户可见文案 → 挂**文案叠加**（术语见 `glossary.md`）：落地前读 `olares-ux-writing` 生成贴近业务的新 key/新文案；收尾委派 `olares-i18n-audit`，**只审本次新增**。硬编码新字符串 → 验收失败；术语/语气 → 记账。缺这两个 skill → **全局安装**后再继续（命令见 `install.sh` / README）。
  - **小修无增量文案**（只改间距/色/结构、或只复用已有 key）→ 不挂 writing skill。
  - **改已有多语言**：用户自己直接调用 writing skill；本链路**不得**间接代劳。
  - **模糊地带必须确认**：分不清「增量 vs 存量」（近义 key 复用还是新建、Figma 与存量略有出入、给旧 key 补 locale、抽 key 时改不改措辞、重命名/合并 key 等）→ **停下来问人**，默认按不动存量处理；禁止自行裁定后改 i18n 文件。问法带上：已有 key/文案摘录、歧义点、建议方案（复用 / 新建 / 请用户直接调 writing skill）。
- **非理想态**：loading / empty / error 必须保留并还原到位。尤其 loading 文案在窄按钮里别换行溢出。
- **a11y**：可聚焦、键盘可达、对比度。
- **动效**：既有过渡不要在重写中消失。**新建动效**须有最小规格（对象、触发、时长、缓动；尊重 `prefers-reduced-motion`），写在 Figma 图层名 / 旁注或运行记录里，落地按规格实现——不是「有科幻感」这类形容词。
- **多形态分支**：standalone / embedded、亮 / 暗、登录 / 未登录等既有分支全部保留。

## 四、复用优先级（自上而下，逐级降级）

先分清两种不同的复用，它们回答的不是同一个问题：

- **第 0 档（任务内部结构复用）**——本次要做的这些模块之间，有哪几个结构相同？它决定**本次要新建几个组件**。
- **第 1–5 档（已有实现复用）**——项目里是不是已经有现成的？它决定**能不能少新建一个**。

两者不可互代。只看第 1–5 档能避开重写已有组件，但拦不住「同一种卡片在同一页里被写了四遍」。

0. **本次任务内部的结构复用**——多个模块结构相同时，抽一个组件用 props 控制差异，不要各写一遍。判定在**写代码之前**完成（长页面档走卡点 4）；一旦开始逐个写，就再没有回头发现的时机。
1. **Code Connect 映射**命中的代码组件——查出来的，最可信。
2. **项目组件库**的现成组件。
3. **姊妹仓库**里对齐了同一设计系统的封装（常能直接移植）。
4. **框架原生组件 + 样式包裹层**：保留原生组件的行为 / 无障碍 / API，只覆盖视觉，样式集中在 wrapper 里，别到处散深选择器和 `!important`。
5. 手写。样式仍走词汇表。

**先搜再写是强制前置检查。** 动手写任何常见控件（dialog / switch / toggle / menu / drawer / tabs / tooltip…）之前必须先搜过 1–3 档。"框架原生够用"不是跳过搜索的理由——项目里往往已有对好了视觉与主题的封装，自己套样式 = 返工。

## 五、工具类优先，自定义 CSS 趋近于零

布局、flex、间距、对齐、显隐、排版、颜色，**一律先找框架 / 项目已有的工具类**，找不到才写 scoped CSS。

不要一上来就造 `.xxx__title` / `.xxx__actions` 这类 BEM 类，再在 `<style>` 里手写 `display:flex` / `gap` / `font-size`。

### ⚠️ 用 token / 变量写进 `<style>` ≠ 合规

在 style 里写 `padding: map-get($space-lg)`、`color: $ink-2`（本可用 `text-ink-2`）、或 `display:flex`（本可用框架 flex 类），**仍然绕过了工具类**。  
只扫裸 `hex`/`px` 会漏掉这类「伪合规」——`design-verify` 已把无豁免的伪合规间距 / 可工具类化布局一并判失败。

**决策顺序（框架无关）：**

1. 项目 / 框架工具类（模板挂 class）
2. 项目扩展工具类（如自建 `flex-gap-*`）
3. 工具类表达不了的组合 → scoped + `design-exempt`
4. 禁止：因「skill 举例里没有」或「顺手改 BEM」就进 style

PC / 移动两套间距且无响应式工具类时：公共档挂模板 class，**只把分叉**写入覆盖或条件 class。

框架专属语法与查证方式（Quasar 的 `q-p*` / `core/*.sass` / `quasar-skilld` 等）写在对应叠加层（Olares → `design-implement-olares`「像开发者一样查」），**不要把某一框架的类名表塞进本文件**。

禁止的合理化：

- 「组件已有 BEM，顺手改 style」→ 先挂 / 改工具类
- 「用了 token 变量，验收能过」→ 不够；有等价工具类就必须用
- 「移动要覆盖，所以整段都写 style」→ 只覆盖分叉
- 「skill 举例没有这个类」→ 去框架源码 / 官方文档查全集，不是手写 CSS 的理由

只有三种情况保留自定义类 / 自定义尺寸字面量，且**必须按下面的固定格式声明豁免**：

1. 固定像素尺寸且无对应工具类（如插画 `240px`）；
2. 主题相关的资源切换（亮 / 暗两张图靠 body 类切 `display`）；
3. 值在词汇表里确实没有匹配项——**或**工具类表达不了的组合（如 `max(..., safe-area)`）。

### 豁免声明的格式（必须逐字照写）

```css
/* design-exempt: <原因> */
.illustration { width: 240px; }
```

```html
<!-- design-exempt: <原因> -->
```

写在被豁免的那条规则或那个元素**紧邻的上一行**。原因要具体到能看出属于上面三种哪一种，例如 `design-exempt: 插画固定尺寸，词汇表无对应档位`。

**为什么要固定前缀而不是"写个注释说明一下"**：`design-verify` 静态层要**机器判定**这一行是不是豁免声明。没有固定模式时它无法区分豁免说明和恰好相邻的普通注释（`/* 卡片容器 */`），于是只有两种坐法：宽松则任何相邻注释都算豁免，豁免机制形同虚设；严格则正常注释被误报为漏声明。

没有 `design-exempt:` 前缀的自定义值 / 伪合规写法，**一律算失败**，不看旁边有没有其他注释。细则见 `design-verify` 静态层。

写每一条 `<style>` 规则前问一遍：这条框架有没有现成工具类？**别凭记忆**——去项目样式目录或框架源码里查。

## 六、UI 可以分文件，逻辑必须共用

PC / Mobile 拆成两个文件时，**只拆模板与样式**。所有业务逻辑（数据获取、状态、事件语义、校验、计算）抽到共享 composable / store，两个文件引用同一份。

**禁止**把同一段逻辑在两处各写一遍。发现逻辑内联在旧组件里，先抽再拆。

## 七、多视口

设计稿要 PC + 移动**两套**（自己生成时也要生成两套）。

缺哪套就**标注降级**，按断点优雅降级，并写进收尾报告。**绝不凭空臆造移动端设计。**

下面这些不只是落地时才看——**在 Figma 生成移动稿时就要算进去**（热区不够、依赖 hover 这类问题拖到落地阶段只能重画）。分文件还是单文件自适应的判断见 `design-implement` 第 3 步的「响应式」一节；分文件时回到上面第六节。

移动端必查：点击热区 ≥ 44px；不依赖 hover 改用 pressed / active；侧栏改 overlay drawer 或底部 sheet；下拉改全屏选择器；底部固定栏留 `env(safe-area-inset-*)`；分清「设备是移动端」与「视口窄」；字号行高用移动端尺度；图片按移动端尺寸导出。

## 八、改了被复用的组件，回去核对所有旧消费者

重构 / 抽取 / 换壳一个被别处引用的组件后，搜出**所有**旧消费者逐个核对，特别是靠 `:deep(.wrapper .xxx)` 这类**依赖你的包裹类名或 DOM 结构**的外部样式。

**删任何包裹层元素或类名前，先确认没有别处的选择器依赖它。**

## 九、失控预算

自主推进不等于无上限。三类容易无限延长的动作各自有止损点：

| 动作 | 上限 | 到顶了怎么办 |
|---|---|---|
| 验收后修正迭代 | 3 轮 | 停下汇报：试过什么 / 差在哪 / 建议怎么办 |
| 探测时找某类定义源 | 同一类值换 3 种关键词 / 路径仍无果 | 当作“该类未找到”记进盘点，继续扫下一类 |
| 找可复用组件 | 按第四节五级走完一轮 | 按第四节降级新写，并写进收尾报告第 3 条 |

后两项**不汇报、不停下**，只是停止继续搜。区别在于：验收反复不过意味着方向可能错了，需要人判断；而搜不到东西只是一个事实，记下来就能继续往下走。

失败本身不打断，超预算才汇报。**搜索无果不能静默**——无论哪一类，停搜的事实都要落到盘点或收尾报告里，否则下一任务会把“没找到”读成“不存在”。

## 十、收尾报告（必须输出）

一份结构化清单：

1. 词汇表里匹配不到、走过卡点 2 的值及处理结果；
2. 缺 Code Connect 映射的组件；
3. 新写（而非复用）的组件及原因；
4. 新导出的资源（路径 / 是否含暗色变体）；
5. 降级项（哪些区块因缺什么而只做了一部分）；
6. 触碰业务逻辑的请求（走过卡点 3 的）；
7. **建议写回 skill 的经验条目**——本次踩到的坑，按「现象 / 根因 / 正确做法 / 建议归到哪个文件」四段写。

第 7 条只是建议。**不要自己去改 skill 文件**，采不采纳由人决定。

人认为这条经验值得留时，它的落点是 skill 仓库的 `docs/inbox.md`（暂存区），**不是直接改 SKILL.md**。当场改正文的结果总是“在最相关那节末尾加一段”，十次之后文件肿成三百行、相似经验散在三处互相矛盾。先攒着，回看时才能看出哪些是同一类问题。

## 十一、外部 skill 找不到时

本链路刻意不重写 Figma API 细节与 Quasar 官方文档，改为**按名字委派**（见 `design-pipeline`「委派怎么写」）。代价是：被委派的 skill 可能没装。

**委派失败**指——agent 的可用 skill 列表里没有该名字，glob 兜底也搜不到文件。这时**不要静默继续**，按依赖性质分两种处理：

### 必需依赖：停下来说

`figma-generate-design` / `figma-use` / `figma-design-to-code` 缺任意一个 → **停下**，告知缺哪个、装在哪、装完怎么继续。

**绝不自己临时实现 Figma API 调用**。手写出来的调用没有官方 skill 的节点语义处理，读回来的图层数据会缺变量绑定和组件实例信息，落地必然对不上——而且表面上看不出异常。

### 可选依赖：降级并记账

`quasar-skilld`、以及 `polish` / `colorize` / `typeset` / `adapt` 那批通用设计 skill 缺失 → **降级继续**：

- 缺 `quasar-skilld` → 改为直接读项目 `node_modules/quasar/dist/api/*.json` 与 `node_modules/quasar/src/css/`。这本来就是更准的源（`quasar-skilld` 镜像的是 2.19.3，可能比项目版本新）。
- 缺通用设计 skill → 按 `design-implement` 的常规流程做，不追求额外的视觉打磨。

两种情况都要把「因缺 X 而降级为 Y」写进收尾报告的降级项（第十节第 5 条）。

### 为什么要区分

不区分的话只有两种坏结局：全部当必需 → 缺个可选 skill 就卡住不干活；全部当可选 → 缺了 Figma skill 也硬着头皮编，产出一份看起来完整、实际全错的代码。
